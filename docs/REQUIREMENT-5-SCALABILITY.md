# المتطلب الخامس · التوسّع وتوزيع الأحمال

**هدف المناقشة** نشغّل ثلاث نسخ تقبل الطلبات من عنوان واحد، ونثبت إنها تتصرف بنفس الطريقة. أثناء 500 طلب منوقف حاوية واحدة والنسختان الباقيتان بتكملوا. ومنشغّل ثلاثة عمّال بريد على نفس الطابور ونثبت إن الطلب الواحد ما بيطلع منه أكثر من تأكيد.

## لوحة العرض في المتصفح

بعد تشغيل بيئة العرض المعزولة، شغّل `.\control-5.cmd` من مجلد المشروع وافتح [مختبر التوسّع](http://localhost:4005). ابدأ بـ«جرّب 9 طلبات» لمعاينة توزيع الطلبات، ثم شغّل العرض الكامل أو اختَر تجربة منفردة. العدّادات وحالة النسخ بتتحدث مع التنفيذ، والسجل بيحفظ نتيجة كل خطوة في الجولة الحالية. زر «شغّل البيئة المعزولة» يقدر يشغّل الحاويات بعد بناء صورها أول مرة، باستخدام مشروع Docker `ecommerce-req5`.

«العرض الكامل» يجري اختبار الحمل، واستمرار البريد، ومنع التكرار، وإعادة اتصال WebSocket، وحدّ تسجيل الدخول المشترك. زر «اختبارات النظام» بيشغّل مجموعة الـ43 اختبار السابقة. بعد اختبار يوصل لحدّ الطلبات، اللوحة بتعرض وقت الانتظار المتبقي قبل إعادته.

## شو كان موجود من قبل؟

| المتطلب | شو بيعمل بالمشروع |
| --- | --- |
| 1. API والأمان | NestJS Gateway يستقبل طلبات المتجر. يتحقق من JWT والدور، وخدمة الطلبات تتحقق من ملكية الطلب. |
| 2. التواصل بين الخدمات | الـGateway يتواصل مع خدمات NestJS عبر TCP. خدمة Go تدير المخزون عبر gRPC وتحجز الكمية بشكل ذري. |
| 3. الأداء | Redis للكتالوج وإشارات القراءة بعد الكتابة، وETag للكتالوج، ونسخة PostgreSQL للقراءة. المخزون يُقرأ من خدمته مباشرة. |
| 4. المعالجة غير المتزامنة | خدمة الطلبات تنشر `order.created`. RabbitMQ يوجّه نسخة لطابور البريد ونسخة لطابور الإشعارات. العامل يرسل عبر SMTP وفيه إعادة محاولة وDLQ. |

## كيف يمر الطلب الآن؟

```text
الويب / الموبايل / Swagger
          │
          ▼
HAProxy :3000
  ├── /api/v1 و/docs  ──> 3 API Gateways ──> خدمات المستخدمين والمنتجات والطلبات
  │                                          └── مخزون Go عبر gRPC
  └── /socket.io/    ──> 3 نسخ إشعارات <────> Redis Pub/Sub

orders-service ──> RabbitMQ
  ├── notifications.events ──> 3 نسخ إشعارات ──> PostgreSQL / Socket.IO
  └── email.order-created   ──> 3 عمّال بريد ──> Mailpit
```

نسخ الـGateway الثلاث تنبني من نفس الصورة. HAProxy يوزّع طلبات HTTP بالدور **Round Robin** ويستثني النسخ التي لا تجيب على فحص الصحة. ترويسة `X-Served-By` بتبيّن أي نسخة ردّت فعلياً. فحص `/health/live` للنسخة نفسها، بينما `/health` بيفحص الخدمات التابعة. الداخلية الخاصة بالإشعارات تمر عبر موزّع TCP على المنفذ 3005 داخل شبكة Docker. [إعداد الموزّع](../docker/haproxy/haproxy.cfg) · [تعريف الحاويات](../docker-compose.yml)

## المشاكل اللي اشتغلنا عليها

| المشكلة | ليش ظهرت مع أكثر من نسخة؟ | الحل وكيف نثبته |
| --- | --- | --- |
| حدّ تسجيل الدخول يتضاعف | كل Gateway كان يملك عدّاداً في ذاكرته. عند التوزيع، المحاولة بتُحسب فقط عند النسخة اللي استقبلتها. | Lua في Redis ينظّف الطلبات المنتهية ويضيف المحاولة ويقرر السماح أو الحظر بعملية ذرية. HAProxy يمرّر عنوان مصدر الاتصال، والـGateway يثق فيه من قفزة واحدة. الديمو يرسل أجسام تسجيل فارغة ليفحص حداً واحداً عبر النسخ الثلاث. |
| الحدث اللحظي يوصل لمجموعة من المتصلين فقط | كل اتصال WebSocket مفتوح فعلياً على نسخة واحدة، بينما RabbitMQ يسلّم الحدث لنسخة إشعارات واحدة وقد تكون مختلفة. | Redis Adapter ينقل البث إلى بقية النسخ. الديمو يشترك بقناة الأدمن من ثلاث اتصالات على ثلاث حاويات ويراقب نفس الطلب. |
| احتمال إرسال نفس التأكيد أكثر من مرة | فحص علامة «أُرسل» ثم الإرسال عمليتان منفصلتان. عاملان ممكن يفحصوا قبل ما يكتب أي منهما العلامة. | حجز ذري مؤقت لكل رقم طلب. العامل الثاني يؤجّل الرسالة، والعامل اللي عنده الحجز يسجّل الإرسال قبل `ack`. لكل تأكيد `Message-ID` ثابت، وMailpit يتجاهل المعرف المكرر. الديمو ينشر 9 رسائل لنفس الطلب ويفحص الصندوق. |
| توقف نسخة أثناء الضغط | إذا كل الطلبات تروح لخادم واحد، توقفه يقطع الخدمة. | ثلاث نسخ خلف HAProxy. نوقف حاوية بعد إرسال أول 200 طلب من أصل 500، ونستمر بالإرسال أثناء التوقف وبعده ونطبع توزيع الردود. |

بإحدى جولات لوحة العرض، رجعت النسخة الجاري إغلاقها بتسعة ردود `503`. كانت تقفل اتصال عدّاد Redis ضمن مرحلة تسبق إغلاق خادم HTTP. صار فصل Redis ضمن مرحلة إتمام الإغلاق بعد انتهاء استقبال الطلبات، حتى يظل العدّاد متاحاً للطلبات التي دخلت وقت الإيقاف. عند إعادة اختبار اللوحة بعد التعديل نجح **500 من 500**، وزمن `p95` بلغ **89 ms** في تلك الجولة.

تجربة WebSocket في اللوحة توقف الحاوية التي كان عليها اتصال الاختبار ثم تفتح اتصالاً جديداً بنفس JWT عبر HAProxy وتتحقّق من الاشتراك بقناة الأدمن على نسخة سليمة. بهالطريقة فيك تثبت إعادة الاتصال والاشتراك من دون انتظار مهلة اكتشاف انقطاع الاتصال القديمة.

**الفرق بين طابورين و3 عمّال** لكل نوع عمل طابوره الخاص. لهذا خدمة الإشعارات والبريد كل واحدة بتاخد حدث الطلب. داخل طابور البريد، RabbitMQ يسلّم كل رسالة لعامل واحد في المحاولة الواحدة. إذا خرج العامل قبل `ack`، الرسالة غير المؤكدة ممكن ترجع للطابور. الحجز وسجل الإرسال يتعاملوا مع هالحالة، وإعادة المحاولة وDLQ من المتطلب الرابع بيضلوا شغّالين. [كود عامل البريد](../backend/apps/email-worker/src/main.ts) · [مبدأ التأكيد وإعادة التسليم في RabbitMQ](https://www.rabbitmq.com/docs/confirms)

## نتيجة التجربة الفعلية

| الفحص | النتيجة |
| --- | --- |
| 500 طلب HTTP للمنتجات والتصنيفات | **500 نجحوا، 0 أخطاء**. زمن `p95` بلغ **74 ms** في هذه الجولة. |
| توزيع أول 200 طلب والنسخ كلها شغّالة | **67 و67 و66**. |
| خلال أمر إيقاف حاوية واحدة | **30 طلباً ناجحاً**. وقت الإيقاف نفسه ممكن يختلف بين تشغيل وآخر. |
| بعد ما أكّد Docker الإيقاف | **135 و135** على النسختين الباقيتين، وصفر على النسخة المتوقفة. بعد إعادتها رجعت تخدم طلبات. |
| حدّ تسجيل الدخول من عنوان واحد | قبل الإصلاح جاء أول `429` عند الطلب **61** لما وزّعنا الطلبات بالتساوي على ثلاث نسخ من الكود القديم. بعد الإصلاح، تسجيل دخول الديمو و19 طلب فحص استنفدوا حد الـ20 المشترك، والطلب التالي رجع **429**. |
| بثّ لحظي عابر للنسخ | حدث طلب واحد وصل **مرة واحدة لكل من 3 اتصالات** على ثلاث حاويات مختلفة. |
| توقف نسخة الإشعارات المتصل بها العميل | اتصال Socket.IO انقطع، والعميل أعاد الاتصال واشترك مرة ثانية بقناة الأدمن والنسختان الباقيتان شغّالتان. |
| عامل البريد أثناء التوقف | نزل عدد المستهلكين من **3 إلى 2**. طلب جديد انحفظ ووصل تأكيده مرة واحدة. وبعد إعادة العامل رجع العدد **3**. |
| إعادة نفس حدث البريد 9 مرات | الكود القديم أرسل **9 رسائل**. الكود الجديد أرسل **رسالة واحدة** وتخطّى 8 عمليات تسليم مكررة. |
| اختبارات النظام السابقة | **43 من 43** نجحوا على تشغيل المتطلب الخامس. تشمل JWT والصلاحيات والملكية، رفع الصور، منع البيع فوق المخزون، البريد، والقنوات اللحظية. |

السيناريو الأول يقيس الاستمرارية على هذا الجهاز وبحمل قراءة صغير. حالة التفرد للبريد مثبتة في Mailpit، والطلب الحقيقي اتجرّب والعمال شغّالين بنسختين.

## التشغيل والتجربة

من مجلد المشروع، مع Docker Desktop شغّال وNode.js مثبت:

```powershell
docker compose up -d --build
npm.cmd --prefix backend ci
.\demo-5.cmd
```

Swagger وREST وWebSocket على `localhost:3000`، الويب على `localhost:3001`، Mailpit على `localhost:8025`، ولوحة RabbitMQ على `localhost:15672`. الديمو الكامل يضيف منتجاً وطلباً تجريبيين ويوقف حاويتين بالتتابع خلال اختبارين مختلفين. يعيد تشغيل أي حاوية أوقفها عند الخروج العادي أو عند فشل اختبار. لتجربة الـ500 طلب فقط شغّل `demo-5.cmd --load-only`. إذا كررت الاختبار الكامل، خلّي نافذة حدّ تسجيل الدخول السابقة تنتهي قبل تكراره.

إذا النسخة السابقة تستخدم المنافذ نفسها، شغّل هذه التجربة بعزل بياناتها ومنافذها:

```powershell
docker compose -p ecommerce-req5 -f docker-compose.yml -f docker-compose.demo.yml up -d --build
npm.cmd --prefix backend ci
.\demo-5.cmd --isolated
```

| خدمة في الوضع المعزول | العنوان |
| --- | --- |
| Swagger | [localhost:13000/docs](http://localhost:13000/docs) |
| لوحة الويب | [localhost:13001](http://localhost:13001) |
| Mailpit | [localhost:18025](http://localhost:18025) |
| RabbitMQ | [localhost:25673](http://localhost:25673) |

ولتجربة اختبارات الـAPI السابقة على المنافذ المعزولة، اترك دقيقة بين الديمو والاختبارات حتى تنتهي نافذة حدّ تسجيل الدخول:

```powershell
$env:API_URL = 'http://localhost:13000/api/v1'
$env:MAILPIT_URL = 'http://localhost:18025'
npm.cmd --prefix backend run test:e2e
Remove-Item Env:API_URL, Env:MAILPIT_URL
```

## كيف تشرحها بالمناقشة؟

1. افتح Swagger ونفّذ طلب المنتجات. شوف `X-Served-By` وكرّر الطلب لتشوف ثلاث قيم.
2. شغّل الديمو. بجدول الـ500 طلب، اشرح أعمدة **قبل الإيقاف، وأثناءه، وبعده**. أسماء الحاويات بتبيّن مين رد بكل مرحلة. `p95` هو الزمن اللي انتهت فيه 95٪ من الطلبات أو أسرع.
3. افتح RabbitMQ على `email.order-created`. اشرح ليش كان العدد 3، وليش يضل البريد شغّال بعد انخفاضه إلى 2. من Mailpit فرجي تأكيد الطلب الحقيقي وتأكّد إن تجربة الرسائل المكررة طلّعت رسالة واحدة.
4. اشرح مثال الإشعار اللحظي. الزبون ممكن يكون متصل بالنسخة الأولى والحدث تعالجه الثانية. Redis Pub/Sub بيوصل البث إلى الأولى، والغرفة وصلاحياتها بيبقوا مثل المتطلب الرابع.

| سؤال متوقع | جواب مختصر |
| --- | --- |
| ليش HAProxy؟ | يوزّع HTTP وWebSocket على المدخل العام، ويدعم TCP الداخلي وفحوصات صحة لكل نسخة بنفس الإعداد. |
| ليش Round Robin؟ | الحاويات متطابقة والاختبار قصده يثبت إن أي نسخة ممكن تجاوب. بالـIP Hash ممكن يخدم مستخدم الاختبار خادم واحد طول الوقت. |
| هل WebSocket بينتقل وهو مفتوح؟ | الاتصال المفتوح ينقطع إذا توقفت حاويته. العميل يعيد الاتصال ويشترك بالقناة مرة ثانية. الـAPI وقاعدة البيانات بيضلوا مصدر حالة الطلب والإشعارات المحفوظة. [توزيع Socket.IO على عدة خوادم](https://socket.io/docs/v4/using-multiple-nodes/) |
| ليش ما منعيد POST تلقائياً عند انقطاع الرد؟ | ممكن يكون الطلب انحفظ والرد هو اللي انقطع. إعادة عملية شراء عمياء ممكن تحجز البضاعة مرتين. HAProxy يعيد المحاولة عند فشل فتح الاتصال فقط. [إعداد HAProxy](https://docs.haproxy.org/3.0/configuration.html#retry-on) |
| هل صفر تكرار مضمون عند أي مزوّد SMTP؟ | الاختبار المحلي يعتمد على أن Mailpit يتجاهل `Message-ID` المكرر. إذا تعطل العامل بعد قبول البريد وقبل تسجيله، ضمان نفس النتيجة خارج Mailpit يحتاج مزوّداً يدعم منع التكرار. [خيارات Mailpit](https://mailpit.axllent.org/docs/configuration/runtime-options/) |
| هل كل البنية مقاومة للأعطال؟ | الاختبار يغطي توقف نسخة من الـGateway أو عامل البريد. HAProxy وRedis وRabbitMQ وPostgreSQL الأساسي وخدمة المخزون خدمات مشتركة، ولكل منها خطة توافر منفصلة لو كان المشروع للنشر الإنتاجي. |
